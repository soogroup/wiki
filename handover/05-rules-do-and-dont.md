# Wiki-Harness 운영 규칙: DO & DON'T

2026-04-16 ~ 2026-05-14 회의록 분석을 통해 도출된 구체적인 운영 규칙

---

## 📋 핵심 규칙 요약

| 카테고리 | DO | DON'T |
|---------|----|----|
| **항목 분류** | 모든 항목을 decision/pending/action/rejected 중 하나로 분류 | "기타" 섹션에 항목 방치 |
| **담당자** | 담당자 미정은 pending으로 올리기 | 담당자 없는 action 생성하기 |
| **결정 변경** | 새 파일 + obsolete 표시 | 기존 파일 덮어쓰기 |
| **Pending** | 재논의_횟수 + 다음_논의 명시 | "다음 회의 재논의"만 기록하기 |
| **Cross-ref** | 파일 간 명확한 링크 설정 | 암묵적 참고 (링크 없음) |

---

## ✅ DO (해야 할 규칙)

### DO#1. 모든 항목을 4가지 카테고리로 분류

**원칙**:
```
모든 회의 안건은 다음 중 정확히 하나여야 함:
- Decision: 무엇을 하기로 결정했는가
- Pending: 다음에 다시 논의해야 하는 것
- Action Item: 누가, 언제까지, 무엇을 할 것인가
- Rejected: 검토했지만 선택하지 않은 것
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
## 기타
재무팀에 정산 프로세스 확인 필요 (담당자 미정)
↑ "기타" 섹션에 방치 → wiki로 분류 안 됨 → 추적 불가능
```

**올바른 예**:
```yaml
# ✅ 좋은 예
# pending-2026-04-16-정산-프로세스-재확인.md
---
타입: pending
보류일: 2026-04-16
주제: 재무팀의 정산 프로세스 확인
다음_논의: "2026-05-14 회의에서 담당자 결정"
---
```

**체크리스트**:
- [ ] 모든 회의 안건이 decision/pending/action/rejected 중 하나?
- [ ] "기타" 섹션에 분류 안 된 항목 있나?
- [ ] 각 항목의 타입 필드가 명시되었나?

---

### DO#2. 담당자 미정 항목은 pending으로 올리기

**원칙**:
```
"누가 할 것인가"가 정해지지 않으면 action_item이 될 수 없음.
담당자 미정 항목은 pending으로 분류하고,
"다음 회의에서 담당자 결정"을 명시.
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
# action-2026-04-16-담당자미정-정산프로세스.md
---
타입: action_item
담당자:  # 빈 칸
마감: 2026-05-14
---
```

**올바른 예**:
```yaml
# ✅ 좋은 예
# pending-2026-04-16-정산-담당자-결정.md
---
타입: pending
주제: 정산 프로세스 확인 — 담당자 결정 필요
다음_논의: "2026-05-14 회의"
---

## 이슈
재무팀의 정산 프로세스를 확인해야 하는데, 
누가 담당할지 아직 결정되지 않음.

## 필요한 것
- 담당 부서/담당자 지정
- 마감일 설정
```

**Lint 규칙**:
```bash
# 담당자 없는 action item 자동 검출
grep -r "담당자.*:\s*$\|담당자.*미정" wiki/action_items/
# 결과가 있으면 error
```

### DO#3. 결정이 변경되면 새 파일 생성 + 이전 파일 obsolete 표시

**원칙**:
```
Decision Revision (결정 번복):
1. 새로운 파일 생성 (결정 날짜 명시)
2. 이전 파일의 상태를 "obsolete"로 변경
3. 새 파일에서 이전_결정 필드로 연결
4. 변경_사유를 명시
```

**예시 (결제 연동 일정 변경)**:

```yaml
# v1: 결제-2026-04-16-pg사-선정-프로세스.md
---
결정일: 2026-04-16
상태: obsolete  # ← 변경됨
---
## 목표
5월 말까지 연동 완료

---

# v2: 결제-2026-05-14-결제-연동-일정-변경.md
---
결정일: 2026-05-14
상태: active  # ← 현재 버전
이전_결정: 결제-2026-04-16-pg사-선정-프로세스.md
변경_사유: A사 스펙 문서 미수신으로 인한 재조정
---
## 변경 사항
5월 말 → 6월 중순으로 연기
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
# 결제-2026-04-16-pg사-선정-프로세스.md 파일을 직접 수정
- 이전: 5월 말
+ 현재: 6월 중순

↑ 이력이 남지 않음, 왜 변경되었는지 불명확
```

**Lint 규칙**:
```bash
# 여러 버전이 모두 "active"인 경우 error
grep -l "상태: active" wiki/decisions/결제-*
# 같은 주제의 파일이 2개 이상 active면 error
```

### DO#4. Pending 항목에 재논의_횟수와 다음_논의 명시

**원칙**:
```
Pending이 여러 회의에서 반복되면:
1. 재논의_횟수를 기록
2. 구체적인 다음_논의 날짜 기입 (또는 "TBD")
3. 2회 이상 재논의되면 상태를 "stale"로 자동 변경
```

**예시 (정산 주기)**:

```yaml
# pending-2026-04-16-정산-주기-재논의.md
---
보류일: 2026-04-16
논의일자: [2026-04-16, 2026-06-11, 2026-07-09]
재논의_횟수: 2  # ← 중요! 3회 논의됨
상태: stale  # ← 2회 이상이면 자동 마킹
다음_논의: TBD  # ← "언제"를 명시
---

## 배경
- 2026-04-16: 월 1회로 결정
- 2026-06-11: 고객사 A의 주 1회 요청 → 재논의 필요
- 2026-07-09: 또 재논의 (결정 못 함)
- 2026-07-23: 아젠다에 올리지 않음 (여전히 보류)

## 상황
3회 논의했지만 여전히 미결정.
강한 의지를 가지고 다음 회의에서는 반드시 결정해야 함.
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
다음_논의: "다음에 재논의"
↑ 구체적 날짜 없음, 몇 번 재논의되었는지 불명

# ❌ 나쁜 예
재논의_횟수: 필드 없음
↑ stale pending 자동 검출 불가
```

**Lint 규칙**:
```bash
# Pending 항목에 다음_논의가 "TBD" 이상 오래된 경우
if 다음_논의 == "TBD" and 보류일이 30일 이상 지남:
  warning: "stale pending — decision 강요 필요"

# 재논의_횟수 >= 2이면 상태 자동 stale
if 재논의_횟수 >= 2 and 상태 != "stale":
  상태 = "stale"
```

### DO#5. Cross-Reference 명확히 설정

**원칙**:
```
Decision과 Action, Pending 간의 참조 관계는 명시적으로 표현.
[[파일명.md]] 링크 또는 frontmatter 필드로 표현.
```

**예시**:

```yaml
# 결제-2026-05-14-결제-연동-일정-변경.md
---
이전_결정: 결제-2026-04-16-pg사-선정-프로세스.md  # ← 역사적 맥락
변경_사유: A사 스펙 문서 미수신
---

## 관련 액션
- [[action-2026-05-14-박준서-a사-연동-스펙-문서-확보.md]]
  (이 결정은 이 액션의 완료에 의존)

---

# action-2026-05-14-박준서-a사-연동-스펙-문서-확보.md
---
의존_결정: 결제-2026-05-14-결제-연동-일정-변경.md
# ↑ Reverse link: 이 액션은 위 결정에 의존
---
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
(링크 없음, 암묵적 참고만)

# 코드를 읽은 사람이:
# - 이전 결정이 뭔지 모름
# - 왜 변경되었는지 모름
# - 관련 액션이 뭔지 모름
```

## ❌ DON'T (하지 말아야 할 규칙)

### DON'T#1. 담당자 없는 Action Item 만들기

**원칙**:
```
Action item의 담당자 필드는 필수.
"미정", "TBD", "?" 등으로 채우면 안 됨.
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
# action-2026-05-14-담당자미정-시스템개선.md
---
타입: action_item
담당자: TBD  # or 미정 or ""
마감: 2026-06-30
---

→ 누가 책임인가? 불명확
→ Lint에서 error
→ 다음 회의에서 또 언급되지 않음 (orphan)
```

**올바른 것**:
```yaml
# ✅ 좋은 예
# pending-2026-05-14-시스템개선-담당자결정.md
---
타입: pending
주제: 시스템 개선 — 담당자 지정 필요
다음_논의: 2026-05-21
---
```

---

### DON'T#2. "기타" 섹션에 항목 방치하기

**원칙**:
```
모든 회의 안건은 wiki 폴더로 분류되어야 함.
"기타"는 일시적 메모일 뿐, 최종 기록이 아님.
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
## 기타
- 재무팀에 정산 프로세스 확인 필요
- 마케팅팀과 협의할 사항 확인
- Q3 일정 재검토

↑ 이 항목들은 decision/pending/action 중 어디?
→ 추적 불가능
→ 다음 회의에서 또 언급될 수도, 안 될 수도...
```

**올바른 것**:
```yaml
# ✅ 좋은 예
# pending-2026-05-14-정산-프로세스-확인.md
# pending-2026-05-14-마케팅-협의.md
# pending-2026-05-14-q3-일정-재검토.md

각각을 명시적으로 분류
```

**Lint 규칙**:
```bash
# Raw source에서 "## 기타" 섹션이 있으면 warning
grep -n "^## 기타" raw-sources/회의록/*.md
# 해당 섹션의 항목이 wiki로 분류되었는지 확인 필요
```

---

### DON'T#3. 기존 파일 덮어쓰기 (결정 변경할 때)

**원칙**:
```
Decision이 변경되었다면:
- 기존 파일을 수정하면 안 됨
- 새 파일을 만들고 이전 파일을 obsolete 표시
- 이렇게 해야 "왜 변경되었는가" 이력이 남음
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
# 결제-2026-04-16-pg사-선정-프로세스.md를 직접 수정:

이전:
---
결정내용: 5월 말까지 연동 완료
---

현재:
---
결정내용: 6월 중순까지 연동 완료
---

↑ 언제 변경되었나? 왜?
→ 이력이 완전히 사라짐
```

**올바른 것**:
```yaml
# ✅ 좋은 예
# 기존 파일은 obsolete 표시:
# 결제-2026-04-16-pg사-선정-프로세스.md
상태: obsolete

# 새 파일 생성:
# 결제-2026-05-14-결제-연동-일정-변경.md
이전_결정: 결제-2026-04-16-pg사-선정-프로세스.md
변경_사유: A사 스펙 문서 미수신
```

---

### DON'T#4. "다음 회의에서 재논의"만 기록하기

**원칙**:
```
Pending을 기록할 때:
- 구체적인 날짜 명시 (또는 "TBD")
- 몇 번 재논의되었는지 기록
- 상태를 "stale"로 표시할 기준 명확히
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
---
타입: pending
다음_논의: "다음 회의에서 재논의"
---

↑ 언제? 몇 번째?
→ 3번째 회의에서도 또 "다음 회의"가 나올 수 있음
→ 무한 보류 (stale pending)
```

**올바른 것**:
```yaml
# ✅ 좋은 예
---
타입: pending
논의일자: [2026-04-16, 2026-06-11, 2026-07-09]
재논의_횟수: 2
상태: stale  # ← 2회 이상이면 자동
다음_논의: "2026-08-06 회의에서 강제 결정" or "TBD"
---
```

---

### DON'T#5. 암묵적 참고 (링크 없음)

**원칙**:
```
파일 간의 참고 관계는 명시적 링크로 표현.
마음으로 "관련 있을 것 같다"는 가정하면 안 됨.
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
# pending-2026-05-14-온보딩-이탈-문제.md
---
설명: 신규 가입자 이탈 심각
---
(링크 없음)

# 그런데 실은 이전 파일과 연관:
# pending-2026-04-16-온보딩-개선-및-대시보드-개편.md

→ 같은 주제의 두 파일이 있는데, 연결 안 됨
→ 나중에 합쳐야 하는지, 별개인지 불명확
```

**올바른 것**:
```yaml
# ✅ 좋은 예
# pending-2026-05-14-온보딩-이탈-문제.md
---
관련_항목:
  - pending-2026-04-16-온보딩-개선-및-대시보드-개편.md
    (같은 주제이지만, 이번은 "이탈" 데이터 분석 필요)
---
```

---

### DON'T#6. 타입 미표시

**원칙**:
```
모든 wiki 파일의 frontmatter는 "타입" 필드를 명시.
decision | pending | action_item | rejected
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
---
출처: raw-sources/...
---
(타입 필드 없음)

→ 이 항목이 뭔지 모름
→ lint/query 자동화 불가능
```

**올바른 것**:
```yaml
# ✅ 좋은 예
---
타입: pending  # or decision, action_item, rejected
출처: raw-sources/...
---
```

---

### DON'T#7. 출처 미명시

**원칙**:
```
모든 wiki 항목은 raw-sources의 정확한 출처 명시.
"어느 회의에서 나온 결정인가" 추적 가능해야 함.
```

**위반 예시**:
```yaml
# ❌ 나쁜 예
---
타입: decision
출처: Notion  # or 빈 칸
---

→ 어느 회의에서 나온 건지 추적 불가능
```

**올바른 것**:
```yaml
# ✅ 좋은 예
---
타입: decision
출처: raw-sources/회의록/2026-05-14-제품주간회의.md
---
```

## 🛡️ Lint 체크리스트 (자동 검출)

### Error (즉시 수정)
```bash
# 1. 담당자 없는 action item
grep -r "담당자.*:\s*$" wiki/action_items/

# 2. 타입 미표시
grep -L "타입:" wiki/**/*.md

# 3. 출처 미명시
grep -L "출처:" wiki/**/*.md

# 4. 상태 미표시
grep -L "상태:" wiki/**/*.md

# 5. 같은 주제의 중복 active decision
grep -h "^타입: decision" wiki/decisions/결제-* | \
  uniq -d | xargs -I {} echo "중복: {}"
```

### Warning (검토 필요)
```bash
# 1. Stale pending (2회 이상 재논의)
grep -B5 "재논의_횟수: [2-9]" wiki/pending/*.md | grep "상태:" | \
  grep -v "stale"

# 2. Pending with "TBD" 다음_논의 (30일 이상)
# 구현 필요

# 3. Orphan items (이전에 언급됐는데 최근 회의에서 미언급)
# 구현 필요

# 4. Broken references
grep -r "\[\[.*\.md\]\]" wiki/ | while read line; do
  file=$(echo $line | grep -o "\[\[.*\.md\]\]" | tr -d '[]')
  [[ ! -f "wiki/$file" ]] && echo "Broken: $line"
done
```

## 📌 최종 체크리스트

새로운 wiki 항목을 만들 때마다:

### 필수 체크
- [ ] 타입이 명확한가? (decision/pending/action/rejected 중 하나)
- [ ] 담당자가 있는가? (없으면 pending으로 올리기)
- [ ] 출처가 명시되어 있는가?
- [ ] 상태가 설정되었는가?
- [ ] 필요한 cross-reference가 있는가?

### Decision 전용
- [ ] 이전_결정 필드는? (revision이면 필수)
- [ ] 변경_사유는? (revision이면 필수)

### Pending 전용
- [ ] 다음_논의 날짜가 구체적인가?
- [ ] 재논의_횟수가 기록되었는가?
- [ ] 2회 이상이면 상태가 "stale"인가?

### Action Item 전용
- [ ] 담당자가 명확한가?
- [ ] 마감일이 설정되었는가?
- [ ] 의존_결정이 있으면 명시되었는가?
- [ ] 상태가 현실적인가? (pending/in_progress/blocked/completed)
