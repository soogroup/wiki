## Q#4a. 영역(Domain) 분류 체계

### 현황
4개 영역이 자연스럽게 나타남:
- 결제 (8개 항목) — 현재 진행 중
- 온보딩 (5개 항목) — 완료
- 정산 (3개 항목) — 보류
- 채용 (1개 항목) — 신규

### 선택지

#### Option A: 파일명 Prefix (구조화된 분류)
```
결제-2026-05-14-pg사-최종-선정.md
온보딩-2026-06-11-3단계-개선-테스트.md
정산-2026-04-16-정산-주기.md
```

**장점**:
- 쿼리 빠름 (`ls 결제-*` 또는 grep `결제-`)
- 파일명에서 주제 한눈에 파악
- index.md에서 영역별 카테고리 정리 용이
- CLAUDE.md의 예제에 이미 반영됨

**단점**:
- 사전에 영역 정의 필요 (새 영역 추가시 논의)
- 경계 영역 분류 애매할 수 있음 ("결제"와 "정산"의 경계?)
- 파일명이 길어질 수 있음

**현재 상태**:
- 2026-05-14까지 이 방식으로 진행 중 ✓

---

#### Option B: 자유로운 태그 (유연한 분류)
```yaml
# 파일명: 2026-05-14-pg사-최종-선정.md
---
tags: [결제, PG연동, 수수료]
---
```

**장점**:
- 유연함 (새 영역/태그 추가 쉬움)
- 하나의 항목에 여러 카테고리 가능
- 조직 구조 변경시 유연함

**단점**:
- 쿼리 복잡도 증가 (tag search 필요)
- 태그 정책이 없으면 산만해짐 ("결제" vs "PG" vs "수수료"?)
- 파일명에서 주제 파악 어려움
- frontmatter 수정 필요

---

## Q#5. Wiki 자동 생성 vs 수동 큐레이션

### 현황
회의록 → wiki 항목 변환 방식 미확정
- 2026-05-14: PM 수동 작성으로 처리
- meeting_minutes.json: 이미 고품질 수동 큐레이션

### 선택지

#### Option A: LLM 자동 추출
```
회의 → Raw source → [LLM] → wiki 분류 → [PM 검수(optional)]
```

**장점**:
- 빠름 (자동화)
- PM의 시간 절감 (회의당 1-2시간 → 0.5시간?)
- 일관된 frontmatter 포맷
- 확장성 좋음 (회의 많아져도 처리 가능)

**단점**:
- **정확도 낮음** ("재무팀 정산" 같은 항목이 decision/pending 중 뭔지 판단 어려움)
- LLM이 decision revision을 판단할 수 없음 (5월 말 → 6월 중순 변경 감지 불가)
- pending 재논의 같은 복잡한 케이스 놓칠 수 있음
- 수정 비용 발생 (자동 추출 후 PM이 검수)
- "담당자 미정" 항목을 action vs pending으로 구분 못함

**리스크**:
- 정확도 낮으면 wiki의 SSOT 역할 상실
- 수정 비용 > 수동 작성 가능성

---

#### Option B: PM 수동 큐레이션
```
회의 → Raw source → [PM이 직접 작성] → wiki 분류
```

**장점**:
- **높은 정확도** (회의 의도 반영)
- decision revision 명확히 판단 (옛날과 지금 비교)
- orphan, stale pending 등 미묘한 케이스 처리 가능
- wiki의 SSOT 역할 보장
- 현재 수준 유지

**단점**:
- PM 시간 필요 (회의당 1-2시간)
- 지표 이상 회의 발생시 bottleneck 가능
- 서식 편차 가능성 (가이드 필수)

**현재 상태**:
- 2026-05-14 ingest: PM 수동 작성으로 완료 ✓
- CLAUDE.md: 수동 큐레이션 프로세스로 정의됨

---

### 📊 비용-효과 분석

| 항목 | Option A | Option B |
|------|---------|---------|
| 회의당 소요 시간 | 0.5h (LLM) + 0.5-1h (수정) = 1-1.5h | 1-2h |
| 월 비용 (4회) | 4-6시간 | 4-8시간 |
| 정확도 | 60-70% (추정) | 95%+ |
| wiki SSOT 신뢰도 | 낮음 | 높음 |
| 의존도 | LLM API 비용, 모델 성능 | PM 역량, 시간 |

---

### 🎯 결정 필요
**Q: 정확도 중심(Option B) vs 자동화 중심(Option A)?**

**선택 기준**:
1. **정확도가 critical한가?** 
   - YES → Option B (wiki는 SSOT이어야 함)
   - NO → Option A (시간이 더 중요)

2. **PM의 시간 여유가 충분한가?**
   - YES → Option B (수동이 정확도 높음)
   - NO → Option A (자동화 필수)

3. **LLM 자동화 인프라 투자 의지?**
   - YES → Option A (장기적으로 이득)
   - NO → Option B (기존 프로세스 유지)

**영향 범위**:
- CLAUDE.md의 ingest 워크플로우 (전체 정의)
- 팀의 반복 작업량
- wiki의 품질 수준
- 향후 6개월+ 지속

**추천 결정 시점**: 즉시 (CLAUDE.md가 이미 수동 기반으로 작성됨)
